# Commit and branch guide (usage reference)

> 🌎 Español: [`git-workflow.md`](git-workflow.md)

This guide documents **how this repository is used through commits**: branch conventions, message
conventions, and examples of the most common operations. It serves as a reference for operating the
repo's GitOps flow (edit the JSON → MR/PR → review → merge → `apply`).

> All examples use **dummy data** (`demo-app`, `data-platform`, folders `demo`/`platform`/`analytics`,
> billing `000000-000000-000000`). Never include real data in commit messages (see
> [§6 Hygiene](#6-hygiene-and-leak-prevention)).

## 1. Purpose

In this repo **the source of truth is `platforms/definitions/project.json`**. Almost every
infrastructure change is an edit to that file. Therefore:

- Each commit represents a **reviewable, auditable** infrastructure change (the JSON diff *is* the change).
- Git history answers "what was created, when, and why".
- A clear commit message + a well-named branch make the Merge/Pull Request quick to review.

## 2. Branch conventions

One branch per unit of work, always starting from an up-to-date `main`.

| Type | Format | When | Example |
|---|---|---|---|
| Feature | `feature/<short-description>` | New projects, folders, services | `feature/add-demo-app-project` |
| Hotfix | `hotfix/<short-description>` | Urgent fix on `main` | `hotfix/fix-demo-labels` |
| With ticket | `feature/<TICKET>-<description>` | If you use Jira/a tracker | `feature/INFRA-123-add-data-platform` |

**Recommendations:**
- Use `kebab-case` and a short, specific English description: `feature/add-analytics-folder`, not `feature/changes`.
- One branch = one goal. Avoid huge branches that mix unrelated projects.

**Avoid:**
- Free-form branches with no prefix or context (`tests`, `datawarehouse2`, `sandbox_final`).
- Branches auto-generated by the web editor (`user-main-patch-12345`): edit locally on a named branch.

## 3. Message conventions (Conventional Commits)

Format: `<type>: <imperative description>`. Standardize in English for consistency.

| Type | Use |
|---|---|
| `feat:` | Add project(s), folder(s), services, or service accounts |
| `fix:` | Fix a wrong value (missing label, incorrect `folder_id`) |
| `refactor:` | Reorganize without changing the outcome (rename, reorder) |
| `chore:` | Maintenance tasks (CODEOWNERS, CI, formatting) |
| `docs:` | Documentation-only changes |

Operation → type mapping:

| Operation in `project.json` | Commit type |
|---|---|
| Add project/folder/service/SA | `feat:` |
| Add missing `bu`/`environment` labels | `fix:` |
| Rename projects / change prefix | `refactor:` |
| Delete an unused project | `refactor:` or `chore:` |
| Change `folder_id` / move to another folder | `fix:` or `refactor:` |
| Update CODEOWNERS / CI | `chore:` |

## 4. Reference table: operation → branch → commit → change

| Operation | Example branch | Commit message | Change in `project.json` |
|---|---|---|---|
| Create folder | `feature/add-demo-folder` | `feat: add demo folder` | New entry in `folders` |
| Add dev project | `feature/add-demo-app-dev` | `feat: add demo-app dev project` | Entry in `projects` (`demo-app-dev`) |
| Add prod project | `feature/add-demo-app-prod` | `feat: add demo-app prod project` | Entry in `projects` (`demo-app-prod`) |
| Add missing labels | `hotfix/fix-demo-labels` | `fix: add bu and environment labels to demo-app` | `labels.bu` / `labels.environment` |
| Enable APIs | `feature/enable-demo-app-apis` | `feat: enable run and bigquery apis for demo-app` | Entry/edit in `project_services` |
| Create service account | `feature/add-demo-app-sa` | `feat: add main-demo-app service account` | Entry in `service_accounts` |
| Rename projects | `refactor/rename-demo-prefix` | `refactor: rename demo projects to demo-app-*` | `name`/`project_id` in `projects` |
| Move to another folder | `fix/move-data-platform-folder` | `fix: move data-platform to platform folder` | `folder_name`/`folder_id` |
| Delete project | `refactor/remove-unused-project` | `refactor: remove unused data-platform-sandbox` | Remove associated entries |
| Update owners | `chore/update-codeowners` | `chore: update default code owners` | (edits `CODEOWNERS`, not the JSON) |

## 5. End-to-end history example

An illustrative `git log --oneline` (most recent on top) of what the repo looks like in use, all with dummy data:

```
a1b2c3d  chore: update default code owners
b2c3d4e  refactor: remove unused data-platform-sandbox project
c3d4e5f  refactor: rename demo projects to demo-app-* prefix
d4e5f6a  feat: add main-data-platform service account
e5f6a7b  feat: enable bigquery api for data-platform-dev
f6a7b8c  feat: add data-platform dev project under platform folder
a7b8c9d  fix: add bu and environment labels to demo-app-prod
b8c9d0e  feat: add demo-app prod project
c9d0e1f  feat: add demo-app dev project and enable run api
d0e1f2a  feat: add demo, platform and analytics folders
```

Typical flow for each of those commits:

```bash
git checkout main && git pull origin main
git checkout -b feature/add-demo-app-dev
# edit platforms/definitions/project.json (add the project)
git add platforms/definitions/project.json
git commit -m "feat: add demo-app dev project and enable run api"
git push origin feature/add-demo-app-dev
# open a Merge/Pull Request and request review (see CODEOWNERS)
```

After approval and merge to `main`, the pipeline runs `terraform apply` automatically.

## 6. Hygiene and leak prevention

Since this is a public reference repo, make sure **neither the commits nor their metadata** expose real data:

- **Git identity**: configure a non-corporate identity before committing.
  ```bash
  git config user.name  "Your Name"
  git config user.email "you@example.com"
  ```
  (The author name and email are stored in every commit forever.)
- **Commit messages**: do not include real people's names, corporate emails, internal project names,
  real folder/billing IDs, or IPs. Use dummy or generic data.
- **Content**: never commit credentials or service account keys. The path
  `credentials/credentials.json` is already in `.gitignore`.
- **Before the first push**, verify there are no leaks:
  ```bash
  git log --pretty='%an <%ae>' | sort -u   # review authors/emails
  grep -rniE 'your-company|@your-domain|real-billing' .   # adjust patterns to your case
  ```
- If you are publishing a repo that had real history, **start a fresh history** (`git init` on the clean
  tree) instead of carrying over the old commits.
